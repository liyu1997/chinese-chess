# 高手与宗师强化说明

本次只强化高手、宗师。前三档的参数和原搜索器保持不变。

## 3倍、10倍的定义

这里是**单步思考时间预算倍数**，不是胜率、Elo、人类段位或可保证的棋力倍数。搜索树的分支数随局面变化，计算量和胜率也不成线性比例。

| 参数 | 高手：旧→新 | 宗师：旧→新 |
|---|---|---|
| 单步时间上限 | 2800→8400毫秒（3倍） | 5500→55000毫秒（10倍） |
| 常规搜索最大层数 | 6→8半步 | 8→12半步 |
| 连续吃子静态搜索上限 | 4→6半步 | 4→8半步 |
| 置换表条目上限 | 60000→120000 | 60000→180000 |
| 近似最优着法容差 | 6分→0分 | 4分→0分 |

“半步”指一方走一次，不是双方各走一次。最大层数是上限；时间到时使用最近完整搜索轮次，不能保证每步都完成8或12层。将军时继续检查合法解将，不在被将军的局面直接按静态分数收手；另设总路径上限防止无限追将。发现确定杀棋可以提前结束。

## 增强原理

1. 加大预算，迭代加深，保留最后一个完整轮次，避免把计算到一半的结果当成最终答案。
2. 主要变化搜索（PVS）：先认真计算最有希望的着法；对其他着法先快速排除，发现更好的候选再完整复查。置换表复用重复局面，历史排序和杀手着法优先检查曾经有效的应对。
3. 高档局面评估新增：车炮活动空间、马腿及机动性、兵卒过河与中路价值、将帅和仕的防守结构。不是仅靠棋子面值决策。
4. 加深吃子推演，减少眼前贪吃后失子。宗师与高手只在已确认等分最优着法之间保留变化；剪枝得到的分数边界不能作为随机选弱招的依据。
5. 搜索在 Web Worker 中进行。宗师复杂局面最多约55秒，界面显示思考上限。后台引擎启动失败时明确提示重试，不再偷偷退回进阶难度。

## 实测记录与局限

测试局面：标准开局，红方中兵前进一步，黑方行棋。随机源固定为0.5，同一执行环境。一次测量结果：

| 指标 | 旧高手 | 新高手 | 旧宗师 | 新宗师 |
|---|---:|---:|---:|---:|
| 实际用时/毫秒 | 2807 | 8400 | 5502 | 55000 |
| 最后完整层数/半步 | 2 | 4 | 3 | 6 |
| 搜索节点 | 43008 | 127840 | 84992 | 953760 |

本样本节点约增加2.97倍、11.22倍；具体数值受设备、负载和局面影响，不能推广为所有棋局的固定提升。节点包括常规搜索与静态搜索，两种搜索的每节点成本也不同。单个开局样本只能证明计算执行与搜索深度改善，不能证明棋力翻倍。

## 难度如何衡量

- **资源指标**：单步时间上限、节点数、最后完整搜索深度；用于确认预算真的生效。
- **战术正确率**：固定测试局面的杀棋发现、避免吃有保护的诱饵、被将军时正确解将；同时检查合法性、调用方棋盘不被修改和预算中断后仍返回合法着法。
- **对弈指标**：固定对手、固定时间控制、多组开局、交换先后手，统计胜/和/负与得分率 `(胜局 + 0.5×和局) / 总局数`；足够样本后才可估计相对Elo和置信区间。本次没有完成大样本新旧引擎对局，不宣称新的Elo或人类段位。

复测：`node tests/ai-strength.cjs`、`node tests/ai-levels.cjs`。
完整时间对比：`node tests/ai-benchmark.cjs /absolute/path/to/old-engine.cjs`。旧引擎可从本变更前提交的 `dist/engine.js` 导出，建议单独运行以减少CPU竞争。
